## 1. 名词表

本轮新增或重新定义的概念（其余已在策划案 §2 中定义的概念继续沿用：

| 名词 | 定义 |
| --- | --- |
| **地块 5 维结构（Tile5D）** | 一个地块用 5 个独立字段描述：北、东、南、西四条边各一种地形，中心一种地形。 |
| **边基础地形（Edge Base）** | 一条边可取的 5 种基础地形：`LAND`、`EMPTY`、`WATER`、`RIVER`、`BANK`（河岸）。`BANK` 是专为河流地块新增的"河岸"地形，可与 `EMPTY` 或 `WATER` 同型对接（详见 §3.2）。 |
| **边修饰（Edge Modifier）** | 可叠加在边基础地形之上的标记，目前仅有一种：`IRRIGATION`（含灌溉节点）。修饰只作用于 `LAND` 和 `WATER`。 |
| **中心地形（Center Terrain）** | 一个地块中央格可取的 4 种地形：`CENTER_LAND`、`CENTER_EMPTY`、`CENTER_LAKE`、`CENTER_RIVER`。 |
| **含灌溉节点的边（Irrigated Edge）** | 带有 `IRRIGATION` 修饰的 `LAND` 或 `WATER` 边。它在拼接时不影响类型判定，但在水源结算里区分"水能否灌溉到 land"。 |
| **水源地块（Water Source Tile）** | 一块实际为所连接的水网贡献水源点数的地块。本轮规则下，`RIVER` 边与 `CENTER_RIVER` 中心**不再贡献水源**，所以"河流地块"不算水源地块；只有 `WATER` / `WATER_WITH_IRRIGATION` / `LAND_WITH_IRRIGATION` 边的地块、以及 `CENTER_LAKE` 地块，仍按 §4.1 贡献水源。 |
| **水渠（Canal）** | 河流地块的 `BANK` 边与外部水口边对接时，被永久改写后形成的"水口边"——它在常规水口基础上额外为所在水网贡献 **6 点**水源容量；多条水渠边对同一水网独立贡献，可叠加。详见 §2.4.4、§4.1。 |
| **种子（Seed）** | 玩家在本轮可用的植物苗源。每位玩家拥有自己的种子集合，集合内三种植物（草 / 花 / 树）并存，详见 §5。 |
| **植物形态（Plant Form）** | 同一地块上的植物在任意时刻只能是下列三者之一：**健康（Healthy）** / **缺水（Water-Short）** / **枯萎（Withered）**。缺水是当前时刻的瞬时状态；枯萎是终局状态，不可逆（游戏结束结算时缺水的植物也算枯萎）。详见 §5。 |
| **扩张（Expansion）** | 玩家主动把植物从一个地块"推"到相邻地块的行为（详见 §7）。扩张是玩家的回合行为，本轮仅在 §5 给出前置语义（"扩张会消耗种子、按某种规则放置植物"），具体节奏在 §7 写作时定。 |

策划案旧名词继续沿用，包括：地块（Tile）、边口（Edge Port）、土地边、水口、空地边、土地块（Land Region）、土地群（Land Component）、水网（Water Component）、灌溉接点（Irrigation Link）、土地单位（Land Unit）。

## 2. 地块 5 维数据结构

### 2.1 数据形状（[已确认]）

一个地块用以下 5 个独立字段描述：

```text
Tile5D = {
    north: EdgeKind,
    east:  EdgeKind,
    south: EdgeKind,
    west:  EdgeKind,
    center: CenterKind
}
```

- `north / east / south / west` 是旋转方向上的固定指代，旋转仅改变其在棋盘上的朝向，不改变字段本身含义。
- `center` 不参与边缘匹配，但参与水源与植物归属结算。

### 2.2 边基础地形（[已确认]）

```text
enum EdgeBase:
    LAND    ; 含可种植土地边的边
    EMPTY   ; 草地 / 留白，无土地无水
    WATER   ; 标准水口
    RIVER   ; 河流（与水口并列的第四种基础地形）
    BANK    ; 河岸（仅河流地块持有；可对接 EMPTY 或 WATER；详见 §2.4.4）
```

**EdgeKind 的实际取值 = EdgeBase + 可选 IRRIGATION 修饰。**

```text
enum EdgeKind:
    LAND                          ; 土地边
    LAND_WITH_IRRIGATION          ; 含灌溉节点的土地边
    EMPTY                         ; 空地边
    WATER                         ; 标准水口
    WATER_WITH_IRRIGATION         ; 含灌溉节点的水口
    RIVER                         ; 河流（不允许带 IRRIGATION 修饰）
    BANK                          ; 河岸（仅河流地块持有；不允许带 IRRIGATION 修饰）
```

### 2.3 中心地形（[已确认]）

```text
enum CenterKind:
    CENTER_EMPTY    ; 中心是空地（草地、留白）
    CENTER_LAND     ; 中心是可种植土地
    CENTER_LAKE     ; 中心是湖泊（新增；等价于策划案里的"泉眼"）
    CENTER_RIVER    ; 中心是河流（新增；视觉/形状不同于湖泊，水量结算同等处理）
```

### 2.4 强制结构约束（[已确认]）

本节定义由中心地形、边基础地形、边修饰组合而成的合法地块形态。一块合法的 `Tile5D` 必须**同时满足** §2.4.1 – §2.4.6 的全部条款。

#### 2.4.1 IRRIGATION 修饰与中心地形的对应规则（[已确认]）

按 IR 修饰子类，给出各自合法的中心地形：

- **[已确认]** `WATER_WITH_IRRIGATION` 边所在的地块，其 `center` 必须为 `CENTER_LAND`。这是唯一允许水网跨界灌溉接口存在的位置；中心是 `EMPTY` / `LAKE` / `RIVER` 时该接口找不到 land 接收方，无效。
- **[已确认]** `LAND_WITH_IRRIGATION` 边所在的地块，其 `center` 必须为 `CENTER_EMPTY` 或 `CENTER_LAKE`：
  - 中心 `CENTER_EMPTY` 时，每条 land 边独立成块，该接口是 land 块单独的灌溉入口；
  - 中心 `CENTER_LAKE` 时，该接口跨越 land↔水网两域，**地块自动并入水网连通集合**（与 §3.3.1 中心 `CENTER_LAKE` 整体并入水网的规则一致，这里是带 IR 修饰的 LAKE 地块的触发条件重申）；
  - 中心 `CENTER_LAND` 时整块 land 区域已合并，再开 LAND 灌溉接口会自灌，配置无效；
  - 中心 `CENTER_RIVER` 见 §2.4.4 与 §2.4.5：河流地块不允许 IR 修饰。
- **[已确认 · 决策一览表]**

| 中心 | `WATER_WITH_IRRIGATION` | `LAND_WITH_IRRIGATION` | 是否自动入水网 |
| --- | --- | --- | --- |
| `CENTER_LAND` | ✓ | ✗ | 否（仅通过其水口边所属外部水网供电） |
| `CENTER_EMPTY` | ✗ | ✓ | 否（land 块自我接水，不入水网） |
| `CENTER_LAKE` | ✗ | ✓ | **是**（地块整体入水网） |
| `CENTER_RIVER` | ✗ | ✗ | 是（地块自身就是水网成员，IR 边不允许） |

#### 2.4.2 中心 = `CENTER_LAND` 时的 land 群约束（[已确认]）

- **[已确认]** 4 条 land 边（含 `LAND` 与 `LAND_WITH_IRRIGATION`）合并成一个**统一的 `land_region`**；中心 `CENTER_LAND` 本身属于该 `land_region`。
- **[已确认]** 由 §2.4.1 决策一览表可得：中心为 `CENTER_LAND` 的地块，IR 修饰只可能为 `WATER_WITH_IRRIGATION`，不可能出现 `LAND_WITH_IRRIGATION`。

#### 2.4.3 中心 = `CENTER_EMPTY` 时的 land 群约束（[已确认]）

- **[已确认]** 中心 = `CENTER_EMPTY` 的地块，4 条边中的所有 land 边**互相独立**，各占一个**独立的 `land_region`**——即使 4 条边全是 land，也算 4 个独立 land 区域，互相不连通。
- **[已确认]** 由 §2.4.1 决策一览表可得：中心为 `CENTER_EMPTY` 的地块，IR 修饰只可能为 `LAND_WITH_IRRIGATION`，不可能出现 `WATER_WITH_IRRIGATION`。

#### 2.4.3.5 中心 = `CENTER_LAKE` 时的地块约束（[已确认]）

- **[已确认]** 中心 `CENTER_LAKE` 的地块**本身即作为整体并入所连接的水网连通集合**（与 §3.3.1 一致）。
- **[已确认]** 由 §2.4.1 决策一览表可得：含 IR 修饰时只可能为 `LAND_WITH_IRRIGATION`，不允许 `WATER_WITH_IRRIGATION`；但当 `LAND_WITH_IRRIGATION` 出现在 `CENTER_LAKE` 地块上时，该地块在地块放下阶段即被强制并入水网连通集合（自动归属，不依赖外部水网连接；具体归属哪个水网由相邻水口/IR 边的连通性决定）。
- **[已确认]** `CENTER_LAKE` 地块上**不需要**任何 `LAND_WITH_IRRIGATION` 也照样入水网——IR 修饰是该地块跨界 land 灌溉接口的开关，不是入水网的必要条件。

#### 2.4.4 中心 = `CENTER_RIVER` 时的河流地块（[已确认]）

河流地块是本规则书新增的**专规类型**，必须同时满足下列全部条款：

- **[已确认]** 河流地块的 `center` 强制为 `CENTER_RIVER`。
- **[已确认]** 河流地块**至少含 1 条 `RIVER` 边**（让中心河道有出口），但允许 1–4 条。
- **[已确认]** 河流地块的边类型**只能取 `RIVER` 或 `BANK`**，**不允许**出现 `LAND` / `WATER` / `EMPTY` / 含 IRRIGATION 修饰的任何边。`BANK` 是专为河流地块新增的"河岸"地形（详见 §1 / §2.2）。
- **[已确认]** `RIVER ↔ RIVER` 拼接合法（同基础地形对接）；不允许 `RIVER ↔ WATER` 的直接拼接；`RIVER ↔ BANK` 也**不允许**直接拼接（详见 §9 #11）。
- **[已确认 · 本轮重大修订]** **`RIVER` 边与 `CENTER_RIVER` 中心都不贡献水源、不组成水网**——它们仅承担"全局唯一完整河流"的连通约束（详见本节末段全局约束条款）。水源贡献走 §4.1：河流地块的 `RIVER` 边 / `CENTER_RIVER` 中心都不命中任何水源档位（按 §4.1 第 4 档 0 点）。
- **[已确认]** 河流地块的 `BANK` 边可与外部水口（`WATER` / `WATER_WITH_IRRIGATION` 基础地形）**对接合法**，对接一旦发生：
  - 该 `BANK` 边被**永久改写为水渠**（详见 §1 / §4.1）：落地形式是 `water_rewrite_at` 字段标记原 `BANK` 边已被水口改写，**保留原 `BANK` 基础类型不动**，但语义上：
    1. 后续所有结算（拼接校验、连通性、水量、灌溉可达）按"水口边"对待；
    2. 该 `BANK` 边按 §4.1 第 5 档（水渠档）为**所在水网**额外贡献 **6 点**水源容量——这是 §4.1 唯一可以"对同一水网叠加获取"的档位（即**多个水渠边各算一份 6 点**，详见 §4.1）。
  - 一旦改写，该边失去 `BANK` 的所有特性（例如它不再与另一侧的 `EMPTY` 拼合法）。
- **[已确认]** 河流地块的 `BANK` 边与外部 `EMPTY` 边对接**合法且不发生改写**——这是 `BANK` 的"本职"对接（BANK ↔ EMPTY 同型合法）。双方保留各自的 `BANK` / `EMPTY` 基础类型，仅作视觉上的"河岸接空地"过渡。
- **[已确认 · 全局连通约束]** **游戏中所有 `RIVER` 边必须构成一条完整的连通河流**（一个 `River Component`，全局唯一）。禁止出现多个互不连通的河流群。任何让 `RIVER` 边落入孤立群的操作（无论放置、改写、扭转）都被规则拒绝——例如新地块的 `RIVER` 边如果会让全局 `RIVER` 集合分裂成 ≥2 个不连通子图，则该放置非法。**该连通约束独立于水网连通**：河流不进入水网连通集合（§3.3.1），仅约束 RIVER 边本身必须全局唯一连通。

#### 2.4.5 `RIVER` 边不允许 IRRIGATION 修饰（[已确认]）

- **[已确认]** `RIVER` 边不允许带 IRRIGATION 修饰。河流本身已经是水源元素，没必要再有"灌溉"标记。

#### 2.4.6 修饰互斥（[已确认]）

- **[已确认]** 同一条边不允许同时叠加两个修饰（目前也只有 IRRIGATION 一个修饰，未来若有新修饰，需保持互斥）。

## 3. 拼接机制

### 3.1 棋盘与旋转（沿用策划案 §4.1）

- **[已确认]** 地块由四条边构成：北、东、南、西；旋转以 90° 为单位；新地块必须至少与一张已有地块边对边相邻（不接受角碰角）。
- **[已确认]** 边界外侧不需要匹配；只有与已放置地块实际接触的边参与校验。

### 3.2 边口类型匹配（[已确认]）

拼接默认只看**边基础地形**，`IRRIGATION` 修饰不参与类型判定。本节共 5 种基础地形：`LAND` / `EMPTY` / `WATER` / `RIVER` / `BANK`。其中 **`BANK` 是专为河流地块新增的"河岸"地形**，对接规则独立于 `EMPTY` ——它可以同型对接 `EMPTY` 与 `WATER`。

| 接触边 | 是否合法 | 说明 |
| --- | --- | --- |
| `LAND` ↔ `LAND`（任一侧可带/不带 IRRIGATION） | 是 | 两侧土地加入同一连续土地群。 |
| `WATER` ↔ `WATER`（任一侧可带/不带 IRRIGATION） | 是 | 两侧水口在边中心点相接，加入同一水网。 |
| `RIVER` ↔ `RIVER` | 是 | 两侧河流连通，加入同一水网。 |
| `EMPTY` ↔ `EMPTY` | 是 | 地貌平滑相接，但不形成土地或水网。 |
| `BANK` ↔ `BANK` | 是 | 仅当两侧均为河流地块时出现（BANK 仅由河流地块持有），作河岸对接处理，不改写、不入水网。 |
| `BANK` ↔ `EMPTY` | **是**（`BANK` 的本职对接） | 河流地块的河岸边与外部空地边对接，**双方基础类型保留不变，不发生改写**，仅作视觉上的"河岸接空地"过渡。 |
| `BANK` ↔ `WATER` / `WATER_WITH_IRRIGATION` | **是 + 触发改写** | 仅当本方为河流地块、邻方为基础水口时才允许（即持有 BANK 的一方必须是河流地块）。对接瞬间该 `BANK` 边被**永久改写为水口**（落字段 `water_rewrite_at`，原 `BANK` 基础类型保留不动），后续所有结算（拼接校验、连通性、水量、灌溉）按"水口"对待。详见 §2.4.4。 |
| 任何其他不同的基础地形 | 否 | 该位置不能放置。 |

**显式约束：**
- `LAND_WITH_IRRIGATION` 与 `LAND` 互接 → **合法**（同属 `LAND` 基础地形）。
- `WATER_WITH_IRRIGATION` 与 `WATER` 互接 → **合法**。
- `LAND` 与 `WATER` 互接 → **不合法**，即便一侧带 IRRIGATION 也不行：IRRIGATION 仅在水源结算里起作用，不改变可拼接类型。
- `RIVER` 与 `WATER` 互接 → **不合法**：`RIVER` 边一律由河流地块持有，对侧也只能是 `RIVER` 边（详见 §2.4.4 与 §9 #11）。
- **`BANK` ↔ `RIVER` / `LAND` 仍不合法**：`BANK` 是河岸，只允许对接 §3.2 表格中明确列出的三类（`BANK` / `EMPTY` / 水口）。
- **`EMPTY` 边 ↔ 水口（`WATER` / `WATER_WITH_IRRIGATION`）整体仍不合法**——`BANK` 是河流地块的专属边类型，**非河流地块**的 `EMPTY` 边和水口对接**仍不合法**（防止规则被广泛滥用）。
- **`BANK` ↔ 水口的改写不可逆**：对接一旦合法且发生，该 `BANK` 边进入"已改写为水口"状态；与已改写边相对放置新地块时按"水口 ↔ 水口"处理；该 `BANK` 边的"原 BANK 身份"只在 UI / 历史日志中可见，不再参与拼接校验与连通集合计算。

### 3.3 拼接后的连通性刷新（[已确认]）

#### 3.3.1 水网连通性的构成（[已确认]）

本节正式定义"水网（Water Component）"的连通判定规则。任何满足下列条件之一的边/地块，并入同一个全局最大连通子图：

1. **[已确认]** 一条 `WATER` / `WATER_WITH_IRRIGATION` 边，与相邻地块同基础类型的水口边拼接后，两侧都加入水网集合。
2. **[已确认]** 任何含 `IRRIGATION` 修饰的边（不论基础是 `LAND` 还是 `WATER`），都**自动并入**连通到的水网集合——即"含灌溉节点"在结算时同等于一个水口接口。
3. **[已确认]** 中心是 `CENTER_LAKE` 的地块，整体并入所属水网集合。
4. **[已确认]** 河流地块**已改写的 `BANK` 边**（即水渠）按水口对待，归属到与对侧水口共属的水网集合；但 **`RIVER` 边与 `CENTER_RIVER` 中心不进入水网**——它们仅承担 §2.4.4 全局连通约束，与水网连通相互独立。详见 §2.4.4 与本节末段说明。
5. **[已确认 · 本轮重大修订]** `RIVER ↔ RIVER` 拼接**不进入水网连通集合**——仅维护 §2.4.4 的"全局唯一完整河流"连通约束，不在水网里产生容量贡献；水流不通过河流段本身流通，河流仅经由河流地块的"水渠边"间接与水网接口。

#### 3.3.2 land 群连通性的构成（[已确认]）

land 群（Land Component）的连通走另一套规则，与水网**互相独立**：

1. **[已确认]** 两条 `LAND` / `LAND_WITH_IRRIGATION` 边对接，且两侧地块的中心都是 `CENTER_LAND` → 两侧 `land_region` 合并为同一 `land_component`。
2. **[已确认]** 两条 `LAND` / `LAND_WITH_IRRIGATION` 边对接，但其中一侧地块中心是 `CENTER_EMPTY` → 两侧 `land_region` **不合并**（中心空地切断）。
3. **[已确认]** 即使 4 条 land 边接的是不同地块，只要每个地块的中心都是 `CENTER_EMPTY`，每条 land 边就属于**独立的** `land_region`——互不连通。

#### 3.3.3 跨界灌溉接口（[已确认]）

- **[已确认]** 含 `IRRIGATION` 修饰的边，作为"land 区域 ↔ 水网"之间的跨界接口：land_region 侧通过该边接收灌溉，水网侧通过同一条边供水。
- **[已确认]** 具体生效条件：
  - `LAND_WITH_IRRIGATION` 边所在的 `land_region` 标记"已被跨界灌溉"；
  - `WATER_WITH_IRRIGATION` 边所在的连通集合标记"已跨界供电"。
- **[已确认]** 单边含 IR（即一侧有 IR、另一侧是普通 `LAND` / `WATER`）也视作有效跨界接口，但只有"对侧也是 IR"时水才能真的流通（否则接口空对地不供电）。

### 3.4 中心地形不参与匹配（[已确认]）

- **[已确认]** 一块地块的 `center` 不会因为它接触的邻居是 `LAND` / `EMPTY` / `WATER` / `RIVER` 而合法或非法。中心只在水源与植物归属阶段起作用。
- **[已确认]** 一个 `CENTER_LAND` 地块可以与四向邻居全是 `EMPTY` 的地块正交相邻；中心土地的扩张由"边对边同型 land 边"驱动，不由中心地形决定。

### 3.5 拼接合法性伪代码（更新版）

```text
can_place(tile, coord, rotation) =
    rotated = rotate(tile, rotation)
    for each face f in {N, E, S, W}:
        neighbor = board[coord + face_offset]
        if neighbor is None: continue                          # 边界外不参与校验
        face_on_tile      = rotated.edge_at(face=f)
        face_on_neighbor  = neighbor.edge_at(face=opposite(f))
        k_tile = base_kind(face_on_tile)
        k_nb   = base_kind(face_on_neighbor)
        # 同基础类型：默认合法（包括 BANK↔BANK、BANK↔EMPTY、BANK↔WATER）
        if k_tile == k_nb: continue
        # 不同基础类型：唯一允许的拼接——河流地块的 BANK ↔ 水口基础类型
        if is_river_bank_water_pair(rotated, neighbor, f):
            mark_pending_water_rewrite(rotated, f)               # 把这条 BANK 边加入"待改写"集合
            continue                                            # 通过校验
        return false                                            # 其他不同基础类型一律拒绝
    return true

is_river_bank_water_pair(my_tile, neighbor_tile, face) =
    my_face = my_tile.edge_at(face=face)
    nb_face = neighbor_tile.edge_at(face=opposite(face))
    # 方向 A：我是河流地块 + 我的这条 BANK 边 + 邻方是水口基础类型
    cond_a = (my_tile.center == CENTER_RIVER
              and base_kind(my_face) == BANK
              and base_kind(nb_face) in {WATER, WATER_WITH_IRRIGATION})
    # 方向 B：邻方是河流地块 + 邻方那条 BANK 边 + 我方是水口基础类型
    # （覆盖"我方先放下水口地块，邻方河流地块"的场景）
    cond_b = (neighbor_tile.center == CENTER_RIVER
              and base_kind(nb_face) == BANK
              and base_kind(my_face) in {WATER, WATER_WITH_IRRIGATION})
    return cond_a or cond_b

# IRRIGATION 修饰不参与 can_place 判定，只参与水源结算。
# center 不参与 can_place 判定（除 §2.4.4 河流地块中心必 RIVER 这一项独立约束）。
# BANK ↔ EMPTY 与 BANK ↔ WATER 都在 §3.2 表格里被列为同型合法，不再走"特例"路径；
# 仅 "是否要永久改写" 由 is_river_bank_water_pair / mark_pending_water_rewrite 决定。
```

## 4. 水网与供水  [本轮重写 v0.2-draft-r10]

本章定义"水如何从水源点出发、经过水网、抵达 land 群并形成灌溉"的完整算法链。本轮重大修订：

- **河流不再贡献水源、不再组成水网**——`RIVER` 边与 `CENTER_RIVER` 中心按 §4.1 第 4 档命中（P = 0），仅承担 §2.4.4 的"全局唯一完整河流"连通约束。
- **水渠（canal）成为新的水源机制**：河流地块的 `BANK` 边与外部水口对接后形成的"水渠边"，按 §4.1 第 5 档为**所在水网**贡献 **6 点**水源容量；多条水渠边对同一水网独立贡献，**可以获取多次**。

本章完整算法链：

```
单地块水源点数 P (§4.1)
  ↓ Σ 累加到水网
水网水源容量 S_W (§4.2)
  ↓ 水网直接灌给每个被灌溉 land_region（不分摊）
单 land_region 实际供水量 V_L = f(S_{K_1}, S_{K_2}, ...) (§4.4)
  ↓ 跨水网合并
枯萎判定：见 §5 植物与归属的"形态判定"小节
```

### 4.1 单地块水源点数 P 与水渠点数（[已确认]）

每块地块对其所属水网 W 贡献一个**地块级**水源点数 P（按四档优先级取档、不叠加）；水网 W 还按"水渠边数量"独立累加一个**边级**水源点数 P_canal（详见本节末段）。两者在 §4.2 一起合并为 S_W。

#### 4.1.1 地块水源点数 P（按四档优先级取档）

| 优先级 | 满足条件 | 地块水源点数 P |
| ---: | --- | ---: |
| 1 | 中心是 `CENTER_LAKE`（未被本节档位提前命中） | **3**（= 1 + 2 的湖泊加成） |
| 2 | 含 `WATER` / `WATER_WITH_IRRIGATION` / `LAND_WITH_IRRIGATION` 之一，且地块内部确实能让水灌溉到 land（即中心 `CENTER_LAND` 或同地块存在 land 节点） | **1** |
| 3 | 完全无上述触发（包括只含 `RIVER` 边 / 中心 `CENTER_RIVER` 但无 WATER / LAKE 的情况） | **0** |
| 4 | 显式黑名单：`CENTER_RIVER` 中心、`RIVER` 边 | **0**（不贡献水源，与原"取档"无关；显式列出防止未来误把河流再算入） |

> 关键点：
>
> - **同地块只取一档**，按"中心 LAKE → 普通有水 → 0"优先级向上取首个命中档；中心 LAKE 单独一块没有水边也没灌溉节点时，第 1 档仍命中（中心 LAKE 是水网元素，本身就给 3 点）。
> - **本轮砍掉原"河流 6 点"档位**——`RIVER` 边 / `CENTER_RIVER` 中心不再贡献水源；它们仅承担 §2.4.4 全局连通约束。
> - 普通水地块若"水穿过地块但无法灌溉到 land"（如 `WATER` 地块 + 中心是空地/湖泊），第 2 档仍命中 1 点——水源贡献只看"是否能入水网"，不要求"是否灌溉到 land"。后者是 §4.5 的判定。

#### 4.1.2 水渠点数 P_canal（按边独立累加，**可获取多次**）

水渠（canal）是 §1 / §2.4.4 定义的"河流地块 `BANK` 边被外部水口对接后形成的永久改写边"。**每条水渠边**为**所在水网**额外贡献 **6 点**水源容量，**与地块级 P 无关，独立累加**：

| 边 | 贡献给所在水网的水源点数 P_canal |
| --- | ---: |
| 每一条被永久改写为水渠的 `BANK` 边（即 `water_rewrite_at` 中标记的边） | **6** |

> 关键点：
>
> - **每条水渠边独立贡献 6 点**，对同一水网可叠加——这是用户原文"可以获取多次"的具象语义：一块水网连接两条河流地块、每条河流地块有两条水渠边，则水渠贡献 = 4 × 6 = **24 点**。
> - 水渠点数是**边级**而非**地块级**：即使两条水渠边都在同一块河流地块上，仍按 2 份 6 点算。
> - 水渠点数的归属是**所在水网**（即该水渠边的对侧水口所属的水网），不是河流自身的全局连通集合——河流本身不组成水网。
> - 水渠点数与地块级 P **不叠加冲突**：地块级 P 算在水网里（按 §4.1.1），水渠点数也算在同一水网里（按 §4.1.2），两者一起贡献 S_W。

### 4.2 水网水源容量 S_W（[已确认]）

每个水网连通集合 W 的**水源容量** S_W 定义为该集合内**地块级 P** + **水渠边级 P_canal** 的总和：

```text
S_W = ( Σ { P_tile | tile ∈ W } )  +  ( Σ { P_canal | canal_edge ∈ W } )
```

> 关键点：
>
> - 一块地块只属于一个水网（连通集合划分是唯一的），不会重复计入。
> - 即使某地块按 §4.1.1 第 3 档命中（P = 0），它仍然属于该水网（只要它有水口边与水网连通）；它对 S_W 的贡献为 0 但仍参与连通分类。
> - 一条水渠边只属于一个水网（同一条边的对侧水口唯一归属一个水网集合），不会重复计入。
> - **水网是 §3.3.1 定义的最大连通子图**。`CENTER_LAKE` 地块按 §3.3.1 隐式入水网，按 §4.1.1 第 1 档给水网贡献 P。`CENTER_RIVER` 地块按 §3.3.1 **不**入水网（仅承担 §2.4.4 全局连通约束），所以即使它含水渠边，那些水渠边也按"对侧水口所在水网"独立贡献。
> - §9 待确认 #7（单水网 S 上限）暂不设：本章 S_W 没有显式上限，单个水网可以无限积累水源容量。

### 4.3 水网对每个被灌溉 land_region 直接灌 S_W（[已确认]）

水网 W 灌溉到的**每一个** `land_region` L，都**直接获得**该水网的全部水源容量 S_W：

```text
L.received_from_W = S_W
```

> **本轮核心规则（沿用 r9："水网供水率为 1，即不需要供水率，对每个 land 的供水量都是 S_W"）**：
>
> - **不引入"供水率 R_W"概念**——水网不需要按 T_W 分摊水量。每个被灌溉 land_region 拿到的就是 S_W 这个"满值"。
> - **不引入"灌溉覆盖 T_W"概念**——T_W 在原分摊公式中是分母，没分摊后 T_W 没有计算意义。
> - 同水网内所有被灌溉的 land_region **拿到的水量彼此相等**（都等于 S_W），不论它们各自与水网有几个 IR 接口——这就是"等量供水"在本轮的具象语义。
> - **S_W > 1 也无所谓**，每 land 单位需水按 §5 植物与归属章节的"植物水量需求"具体数值；多余水量不浪费但也不溢出到其他 land。

### 4.4 单 land_region 的实际供水量 V_L（[提案]）

一个 `land_region` L 实际接收到的总水量由其连接的所有水网 K_1, ..., K_n 的 S 值共同决定：

```text
V_L = ⊕ ( S_{K_1}, S_{K_2}, ..., S_{K_n} )
```

> **关键点**：
>
> - 每个水网对 L 的贡献是独立的 S_{K_i}（每条水网灌"一整份"给 L，不分摊）。
> - ⊕ 是水网间的"合并算子"（详见 §9 待确认 #13）。
> - **本节是 [提案]**：默认 ⊕ = sum；候选 max / 主水网选择。

### 4.5 灌溉接点的语义边界（[已确认]）

确认"什么算成功灌溉、什么不算"——本节对应"同一 land_region 对同一水网只算 1 次"的核心规则：

- **[已确认]** "成功灌溉" = `land_region` L 通过至少一个 IR 接口接通水网 W（§3.3.3 跨界接口判定）。此时 L 直接获得 S_W（按 §4.3）。
- **[已确认]** **同一 `land_region` 对同一水网只算 1 次**：即使 L 对水网 W 有多个 IR 接口（例如地块 a 同时含一条 `WATER_WITH_IRRIGATION` 边和一条 `LAND_WITH_IRRIGATION` 边都通向水网 W），L 从 W 拿到的水量仍是 S_W，**不会变成 N × S_W**。
- **[已确认]** **不同 `land_region`（即使在同一地块上，例如中心 EMPTY 时每条 land 边各算一块）独立计数**：每块 land_region 都各自从其连接的水网拿到完整的 S_W。
- **[已确认]** "水穿过但不灌溉"的情形（普通 `WATER` 地块、中心非 `CENTER_LAND`）不构成 IR 接口——水从这块地穿过但没有 IR 跨界接口，因此 L 不算被该水网灌溉到。
- **[已确认]** 没有 IR 接口的水口边（普通 `WATER`）只参与水网连通（§3.3.1），不参与灌溉。
- **[已确认 · 本轮新增]** **水渠边（`water_rewrite_at` 标记的 `BANK` 边）的对接关系**：水渠边算作水口，但**它的对接侧是普通水口，不是 land**——水渠边不直接给 land 灌水；它给所在水网贡献 P_canal，所在水网再通过其普通 IR 接口把 S_W 灌给 land。这就是"水渠通过水网"间接灌溉 land 的完整链路。

## 5. 植物与归属  [本轮重写 v0.2-draft-r10]

本章定义"每位玩家拥有的种子如何在游戏过程中放置、扩张、获取水源、判定形态"的全套规则。

> **本轮新增**：v0.2 引入完整的植物系统；v0.1 策划案里"植物"作为标签，本章才正式落地为有三种形态、三种需水量的可结算对象。

### 5.1 玩家、种子、地块的关系（[已确认]）

- **[已确认]** 每位玩家拥有自己**独立**的种子集合：集合内三种植物（草 / 花 / 树）并存，玩家可按 §7 节奏消耗种子扩张（详见 §7，本章仅描述植物本身的规则）。
- **[已确认]** 玩家在放置植物时只能从自己的种子集合里取；不允许借种、换种、共用。
- **[已确认 · 本轮新增]** 种子是**扩张时消耗**、**全封闭时退还**的资源——扩张时扣 1 枚对应种类种子（§5.8）；§5.6 全封闭结算时该 land_region 上每棵植物退还对应种类种子 1 枚；§5.7 游戏结束结算时不再退还（仅形态升级，不退种）。WITHERED 形态不可逆——一旦进入 WITHERED 且所在 land_region **未**封闭，种子不会被退还（这是 WITHERED 的"永久性"和"封闭退还"的区别）。
- **[已确认]** **同一地形块（即同一个 Tile5D 实例，对应棋盘上一格）可以同时生长多种植物**——但是**同一种植物在该地形块上只能属于一个玩家**。即：
  - 一格可同时拥有"草（玩家 P1）+ 花（玩家 P2）+ 树（玩家 P3）"三种并存。
  - 一格**不允许**同时有"P1 的草"和"P2 的草"——草种在该格上必须有且仅有一个主人。
  - 一格**不允许**同时有"P1 的花"和"P2 的花"——花种在该格上必须有且仅有一个主人。
  - 一格**不允许**同时有"P1 的树"和"P2 的树"——树种在该格上必须有且仅有一个主人。
  该限制与"土地块（`land_region`）"是不同层级：
  - "地形块（Tile）"= 棋盘上一格，由 5 维结构描述（§2）；
  - "土地块（Land Region）"= 由若干地形块的 land 边围成的连通区域（§3.3.2）。
- **[已确认 · 本轮新增]** **物种/玩家二元归属**：每棵植物 `p` 同时绑定两个属性——`p.species ∈ {GRASS, FLOWER, TREE}` 与 `p.owner ∈ Players`。同一格同物种唯一主人；不同物种在同一格可以属于不同玩家。归属由扩张动作（§5.8）显式指定，不存在"自动归属"或"按地块颜色归属"。
- **[已确认 · 本轮新增]** **扩张撞同物种冲突默认行为**：玩家 P 试图把物种 S 的植物扩张到某格 `t`，若 `t` 上已存在物种 S 且属于其他玩家 P'，扩张视为非法（被原主同种植物阻挡）；同种同主（P 自己在 t 上已有物种 S）则视为"地块已占据，不重置"扩张失败。具体回滚/抢占/换主等高级语义见 §9 #19。
- **[已确认]** 一个 `land_region` 内可以有**多棵**植物，分别种在不同地形块上；只要这些地形块都属于同一 `land_region`，它们共享水源（按 §4.3）。同一格多物种时，每物种仍独立耗水（草耗 0.5、花耗 1、树耗 2），彼此不抵消。
- **[已确认]** 玩家扩张时只能把植物推到**与已有己方植物所在 `land_region` 相邻**的地形块上（详见 §7）。换言之，每位玩家的植物连片占据一个或多个 `land_region`。
- **[已确认 · 本轮新增]** **缺水形态可逆**——`HEALTHY ↔ WATER_SHORT` 双向切换由 §5.4 / §5.5 / §4 决定：当 `land_region` L 的 V_L 增加时，下一次结算该 L 上的缺水植物可恢复为 HEALTHY；V_L 减少时同样可由 HEALTHY 退化为 WATER_SHORT。**唯独 WITHERED 不可逆**（详见 §5.3 / §5.6 / §5.7）。这是本轮与 v0.2-draft-r10/r11 的核心差异之一。
- **[已确认 · 本轮新增]** **全封闭 land_region 退还种子**——当 `land_region` L 被判定为"全封闭"时（按 §5.6 的判定），L 上**所有玩家所有植物**统一被移除，且每棵被移除的植物**退还对应种类种子 1 枚**给原拥有者。退还按物种对应（同格多物种各自退各自种类的种子）；退还时点的精确语义、是否同时触发枯萎升级见 §5.6。这是本轮与 v0.2-draft-r10/r11 的核心差异之二。

### 5.2 三种植物与水量需求（[已确认]）

| 植物 | 每地块需水量 `need` | 数量级 | 战略定位 |
| --- | ---: | --- | --- |
| **草（Grass）** | **0.5** | 低 | 门槛最低的"基底植物" |
| **花（Flower）** | **1** | 中 | 标准植物 |
| **树（Tree）** | **2** | 高 | 门槛最高的"主力植物" |

> 关键点：
>
> - `need` 值定义在 §5.4 / §5.5 的判定公式里：玩家某棵植物 `p` 所在 `land_region` L 的实际供水量 V_L 与 `p.need` 比较，决定 `p` 当前的形态（§5.3）。
> - `need` 是**单地块**需水量（用户原文："每一个地形块上的草需要 0.5 水源"），与 §4 的 S_W / V_L 都是同一量级——本规则书统一以"水源点数"为度量，不引入分数。
> - **同一地块可以多种植物并存**（§5.1）：一格可同时长"草 + 花 + 树"，但**同种植物在同一格上只能属于一个玩家**。
> - **三种植物的需水量互相独立**：草在该格耗 0.5 单位、花在该格耗 1 单位、树在该格耗 2 单位——若一格同时有草和花，则该格对所在 `land_region` 的水源消耗 = 0.5 + 1 = 1.5。同一格同物种不会被同一玩家重复种多次（一条扩张仅在该格产生一棵该物种的植物）。

### 5.3 植物形态（[已确认]）

任意时刻，每棵植物 `p` 处于下列三种形态之一：

| 形态 | 含义 | 是否终局 | 进入条件 |
| --- | --- | --- | --- |
| **健康（Healthy）** | 正常生长，可参与计分（§6） | 否，可转入缺水 | V_L ≥ `p.need`（详见 §5.4） |
| **缺水（Water-Short）** | 当前水源不足，但仍在挣扎 | 否，可转入枯萎 | V_L < `p.need`（详见 §5.4） |
| **枯萎（Withered）** | 死亡，不可逆 | **是** | 缺水达到 §5.6 触发条件；或游戏结束结算时仍处于缺水状态（§5.7） |

> 关键点：
>
> - **形态是单棵植物的属性**——不是地块、不是 `land_region`。一格一形态。
> - 形态变更由 §5.4 / §5.5 / §5.6 / §5.7 驱动。
> - **[已确认 · 本轮新增] HEALTHY ↔ WATER_SHORT 可逆**——下一次结算按当时的 V_L 重新判定（V_L 增长可从 WATER_SHORT 恢复 HEALTHY，V_L 减少可从 HEALTHY 退化为 WATER_SHORT）。
> - **[已确认]** **WITHERED 不可逆**——在未封闭 `land_region` 上枯萎形态的植物既不能恢复健康，也不能"恢复退还的种子"。一旦某 `land_region` 在 §5.6 全封闭结算中被清场，已 WITHERED 的植物也走"退还种子 + 移除"流程（与健康的、缺水的同等处理），但 WITHERED 标记仅在移除前那一刻的形态枚举里有意义。

### 5.4 缺水判定规则（[已确认 · 本轮重写 v0.2-draft-r12]）

> **本轮重大修订**：用户的原话是"缺水只对当前土地块的植物生效，没有全局影响"——本节据此取消 v0.2-draft-r10/r11 的所有三物种"传播规则"（草传该 land_region 上所有该玩家的草、花全局传染、树传最后扩张）。所有物种（草 / 花 / 树）的缺水都是**单棵单 land_region** 判定；草 / 花 / 树之间的"差别"不再出在 §5.4（缺水判定），而是统一回到 §5.5（水量分配的优先级）。
>
> 同时确立**缺水形态可逆**（与 §5.1 / §5.3 锁定的 §5.3 可逆性一致）。

每次结算时（结算时机见 §5.5 / §5.6 / §7），按下述算法判定每棵植物的形态：

```text
for each plant p (无物种区分):
    let L = land_region containing p
    let V = V_L (按 §4.4 计算)
    if V ≥ p.need:  p.form = HEALTHY        # 可逆，下次 V_L < p.need 时再退化
    else:           p.form = WATER_SHORT    # 可逆，下次 V_L ≥ p.need 时恢复
    # WITHERED 判定见 §5.6 / §5.7
```

> 关键点：
>
> - **[已确认 · 本轮用户原话]** "**缺水只对当前土地块的植物生效，没有全局影响**"——三条传染全部废除。
>   - **草**：单棵 `V_L ≥ 0.5` 健康，否则缺水；不再向所在 `land_region` 上的其他草传染。
>   - **花**：单棵 `V_L ≥ 1` 健康，否则缺水；不再向该玩家全局所有花传染。
>   - **树**：单棵 `V_L ≥ 2` 健康，否则缺水；不再向"最后扩张的树"特殊传染。
> - **HEALTHY ↔ WATER_SHORT 可逆**：V_L 增加可恢复、减少可退化，唯独 WITHERED 不可逆。
> - **[已确认 · 本轮用户原话]** "**草会优先获取水源，所以如果草缺水，土地块上的其他植物也一定缺水**"——这是 §5.5 Step A 草优先的**自然推论**，不是显式传染规则。机理：草优先拿水（每棵 0.5）；若 L 上的草导致 Step A 结束后 V_L 已近 0（或 < 0.5），Step B / C 拿到的已经是耗剩的 V_L，花 / 树自然全缺水。语法上"草缺水→其他一定缺水"成立，但**没有跨棵的传染代码**——它就是 Step A 的算术结果。
> - WITHERED 不在 §5.4 进入——仅由 §5.6 全封闭结算（或 §5.7 游戏结束结算）升级而来。
> - **§9 #16 / #17 已作废**（草"所有植物"=？、花全局传染）：本节一并解决，详见 §9。

### 5.5 水源分配优先级（[已确认]）

每位玩家的植物在某次结算时争夺 `land_region` L 的供水量 V_L 时，按下列**优先级**分配：

1. **[已确认]** **草优先**——所有草的需求最先被满足；草拿完所需后才进入花 / 树的分配。
2. **[已确认]** **花与树优先级相同**——剩余的 V_L 在花和树之间**对半分**；任何一方仍有剩余时（即 `take > need_xxx`），剩余水源**补给对方**（直至双方都满足或 V_L 耗尽）。
3. **[已确认]** **跨玩家**：水源分配按 §5.5 优先级在所有玩家之间统一排队——草的需求先于花/树，不论玩家归属。
4. **[已确认]** **整体流程（伪代码）**：

```text
# 输入：land_region L 的供水量 V_L，以及 L 上所有植物（含所属玩家）
# 输出：每棵植物的形态（HEALTHY / WATER_SHORT）

# Step A: 草拿满（即使 V_L 还有剩余，草也不会透支花 / 树的水——Step B 才会重新进入分配）
for each plant p in [GRASS]:
    if V_L >= p.need:            # p.need == 0.5
        V_L -= p.need
        p.form = HEALTHY
    else:
        p.form = WATER_SHORT      # 即使 V_L 还有剩余，也不会让花 / 树多分

# Step B: 剩余 V_L 在花 / 树之间对半分
half = V_L / 2
# B.1: 花拿 half
flowers = [plants in [FLOWER]]
need_F  = count(flowers) * 1
take_F  = min(half, need_F)
for i in 0..take_F/1:   flowers[i].form = HEALTHY
for i in take_F/1..:    flowers[i].form = WATER_SHORT
remain_F = max(0, half - need_F)
# B.2: 树拿 half
trees   = [plants in [TREE]]
need_T  = count(trees) * 2
take_T  = min(half, need_T)
for i in 0..take_T/2:   trees[i].form = HEALTHY
for i in take_T/2..:    trees[i].form = WATER_SHORT
remain_T = max(0, half - need_T)
# Step C: 双方剩余互相补给
extra_F = min(remain_T, need_F - take_F)   # 树剩余补给花
extra_T = min(remain_F, need_T - take_T)   # 花剩余补给树
for i in take_F/1 .. take_F/1 + extra_F:   flowers[i].form = HEALTHY
for i in take_T/2 .. take_T/2 + extra_T:   trees[i].form = HEALTHY

# Step D: [本轮作废 v0.2-draft-r12] §5.4 种类特性覆盖规则已废除——
#   基础判定（Step A/B/C）即最终形态；不再有"草传草 / 花传花 / 树传最后扩张"的
#   跨棵传播。HEALTHY / WATER_SHORT 形态在结算末尾保持 Step A/B/C 的结果即可，
#   下次结算时按当时的 V_L 重新计算。
```

> 关键点：
>
> - **草拿完 → 花 / 树各分一半 → 互相补给** 是用户原文的逐字翻译：
>   > "草会优先拿走所有需要的水源，剩余的给花和树；花和树优先级相同，即花和树会先分走剩余水源的一半，如果花/树仍剩余，会分给对方"。
> - **草不会透支花 / 树的水**——Step A 严格按"草拿满"，即使 V_L 还有剩余也不会让花 / 树多分；Step B 才重新进入分配。
> - **[已确认 · 本轮新增 · 用户原话]** "**如果草缺水，土地块上的其他植物也一定缺水**" 是 Step A 草优先的算术推论：草优先拿水，V_L 不够时 Step A 拿完 V_L 趋零；Step B / C 自然拿不到水，花 / 树全缺水。这是规则**自然结果**而不是跨棵传播，**没有显式传染代码**。
> - 草是单棵 0.5 单位，可能出现"半单位"分配（V_L = 0.5 时 1 棵草恰好满足，多于 1 棵则剩余 0 进 Step B；详见 §9 #15）。
> - 同一个 `land_region` 上**只有一位玩家**的实际场景下，"对半分"等价于"全部可用"——即该玩家独享，不影响算法语义。
> - **[已确认 · 本轮作废] Step D 覆盖规则**（v0.2-draft-r10/r11 中"草/花/树各自的传播范围"在末尾覆盖基础判定的逻辑）已废除——Step A/B/C 给出的形态就是最终形态。§5.6 全封闭枯萎入口独立于 §5.5，枯萎升级按 §5.6 的"阶段 A 升级"判定。

### 5.6 全封闭与枯萎判定（[已确认 · 本轮重写 v0.2-draft-r12]）

> **本节是 §5.3 枯萎形态的正式入口**，同时也是**退还种子的触发器**。本轮把 §5.6 重写为两阶段流程：**阶段 A 升级枯萎**（仅当关联水网也全封闭）→ **阶段 B 不论形态退还种子 + 清场**（仅当 land 边全封闭）。

#### 5.6.1 全封闭定义（[已确认]）

- **[已确认]** "全封闭"由下列两者同时满足：
  - **土地块全封闭**：一个 `land_region` L 的所有 `land` 边都被其它已放置的地块的同型 land 边对接——L 不会再扩张（即无法再拼接新的 land 地块）。
  - **对应水网全封闭**：与 L 关联的（按 §4.5 跨界接口判定）每个水网 W，也都满足"全封闭"判定——W 的所有可扩展边界都已被对接。
- **[已确认]** **全封闭是结算时点的瞬时状态**，每次结算时由规则重新判定。
- **[已确认]** "**部分封闭**"——即 L 满足 land 边全封闭但**关联水网不全封闭**——仍是合法的触发状态，但只触发**退还**（§5.6.2 阶段 B），**不触发枯萎升级**（跳过阶段 A）。这也契合用户原话："当一个土地块完全封闭，不管植物怎么样，都会归还所有玩家投入的种子；当一个土地块封闭，并且对应的所有水网也封闭，则缺水植物变为枯萎"——前者是 land 边全封闭就能触发，后者额外加了水网全封闭才升级枯萎。
- **[待确认]** "水网全封闭"目前没有具体算法（§9 待确认 #14）；本节先按"全封闭"语义上锁定，等 §7 写作时一起定义。

#### 5.6.2 全封闭结算流程（[已确认 · 本轮重写]）

每次结算时（结算时机见 §7），按下述两阶段顺序处理每个 `land_region` L：

```text
on_settle_land_region(L):
    if not (L is land_closed): return   # 仅 land 封闭才走本流程；半封闭/未封闭跳过

    # 阶段 A: 升级枯萎（仅当关联水网也全封闭时执行）
    #   用户原话："当一个土地块封闭，并且对应的所有水网也封闭，则缺水植物变为枯萎"
    if every W in attached_water_components(L) is water_closed:
        for each plant p on L:
            if p.form == WATER_SHORT:  p.form = WITHERED   # 不可逆
            # 健康或 WITHERED 保留——健康不会因封闭而枯萎
            # WITHERED 形态不在本阶段再处理

    # 阶段 B: 不论形态，统一退还种子 + 清场
    #   用户原话："当一个土地块完全封闭，不管植物怎么样，都会归还所有玩家投入的种子"
    for each plant p on L:
        refund_seed(p.owner, p.species, 1)   # 按物种对应退还 1 枚种子给原主
        remove(p)                             # 从 L 与棋盘移除

    # L 进入"已退还"状态——后续不再有植物，也不参与新一轮结算
```

> 关键点：
>
> - **退还与枯萎是两条独立触发器**——前者仅需 land 边全封闭；后者额外要求水网全封闭。
> - **阶段顺序：A 在 B 之前**——保证 WITHERED 标记在退还前被正确写入被清退的植物；阶段 B 涉及的所有植物（含 WITHERED、健康、缺水的）一律退还。WITHERED 标记虽然不再影响后续（因为植物即将被 remove），但保持流程一致：先把所有"形态最终态"确定，再统一退还。
> - **退还按物种对应**——一棵草退 1 枚草种；一棵花退 1 枚花种；一棵树退 1 枚树种；同格多物种各自退各自种类的种子。退还归属 `p.owner`，与原扩张动作一致。
> - **健康植物不退化为枯萎**——即使全封闭也不影响 HEALTHY 形态；它们在阶段 A 通过 if 判定保留 HEALTHY，在阶段 B 走退还+移除。
> - **[已确认]** WITHERED 形态的植物**也退还种子**——本节统一处理（含 §5.7 游戏结束结算时如果某 land_region 仍处全封闭，则同样按本流程触发）。这与 v0.2-draft-r10/r11 "枯萎不放回种子" 的表述有差异，本节修订为"任何状态都退，枯萎只是形态标记"。
> - 全封闭判定**与水源重新供给的能力有关**：例如 L 接 W_1（封闭）、W_2（未封闭），L 是 land 边全封闭 → 触发阶段 B（退还），但**不**触发阶段 A（升级枯萎）。这是用户"两个条件独立"语义的直接落地。

### 5.7 游戏结束结算（[已确认 · 本轮修订 v0.2-draft-r12]）

> 游戏结束的具体触发条件（牌堆耗尽、N 轮后、各玩家连续 Pass N 次等）见 §6 计分与胜负，本节只锁定结算口径。
>
> **本轮修订**：§5.7 的范围**收窄**——只做"形态升级"（缺水 → 枯萎），**不再**触发 §5.6 的阶段 B 退还种子。退还种子的时点固定在 §5.6.2 的 §7 持续结算时点（即每个 §5.6 触发窗口内）。游戏结束时刻假设 §5.6 已对所有"已封闭"的 land_region 跑过阶段 A + 阶段 B，剩余的 land_region 都是"未封闭"——§5.7 对剩余的做最后一次形态结算。

游戏结束时刻，按下述流程对**剩余未封闭**的 `land_region` 跑最后一次形态结算：

```text
on_game_end():
    # 阶段 0: §5.6 全封闭结算（仅对剩余未封闭跳过；已封闭状态在 §7 持续结算已处理）
    #   若 §7 设计上要求"游戏结束触发一次清理"，该窗口可在此处显式调用 on_settle_land_region(L)
    #   当前默认 §7 持续结算已覆盖，故不重复
    
    # 阶段 1: 重新结算水源（§4 + §5.5）
    recompute_all_V_L()                  # 按 §4 重算所有 land_region 的供水量
    apply_water_priority_to_all()        # 按 §5.5 重分配所有水源

    # 阶段 2: 终局形态结算（用户原话："游戏结束结算时，缺水的植物也会枯萎"）
    for each plant p:
        if p.form == WATER_SHORT:
            p.form = WITHERED            # 不论其所在 land_region 是否全封闭——终局缺水 = 枯萎

    # 阶段 3: 进入 §6 计分（只有 HEALTHY 形态参与计分）
    score_all()                          # 详见 §6
```

> 关键点：
>
> - **[已确认 · 本轮修订]** **游戏结束结算仅升级枯萎，不退还种子**——退还路径已在 §5.6 / §7 持续结算时点处理。若 §7 设计上要求把退还延迟到游戏结束统一触发，等 §7 写作时再调整入口位置（不影响 §5.6 的算法语义）。
> - **缺水的植物在游戏结束时也进入枯萎**——这是用户原话："游戏结束结算时，缺水的植物也会枯萎"。
> - **计分只算 HEALTHY**——WATER_SHORT 与 WITHERED 都不参与最终得分（详见 §6）。
> - 全封闭触发的枯萎（§5.6 阶段 A）与游戏结束触发的枯萎（§5.7 阶段 2）**都会让植物失去得分资格**——这两种是同一终局状态的两种入口。但前者会同步退还种子；后者不再退还。

### 5.8 与 §7 扩张行为的前置接口（[已确认]）

为 §7 写作预留前置语义，本章涉及的扩张相关属性：

- **[已确认]** 玩家的"扩张"指把一棵植物从已有己方植物所在 `land_region` 推到相邻地形块（§5.1）。
- **[已确认]** 扩张消耗**对应种类**的种子——草扩张消耗草种子 1 枚；花消耗花种子 1 枚；树消耗树种子 1 枚。
- **[已确认 · 本轮新增]** **扩张合法性前置检查**（在扣种子之前执行，失败则不消耗种子、不留痕迹）：
  1. 目标格 `t` 必须与已有己方植物所在 `land_region` L 相邻（与既有规则一致）；
  2. 目标格 `t` 上**不能**已有"其他玩家同物种的植物"——即撞同种异主视为扩张非法（详见 §5.1 / §9 #19）；
  3. 目标格 `t` 上**可以**已有"同一玩家的同物种植物"以外的任意组合——即允许"在已有 P2 花的格子上扩张 P1 的草"（草 / 花是不同物种），也允许"在没有任何植物的格子上扩张任一物种"。
- **[已确认]** 扩张放置的植物初始形态为 **HEALTHY**——只要扩张那一刻该 `land_region` 的 V_L ≥ `p.need`，扩张成功且健康；否则扩张仍然允许放置但立即进入 WATER_SHORT 状态（按 §5.4 / §5.5）。
- **[已确认]** **扩张顺序由玩家行为序列决定**——这是为 §7 与 §6 留的前置接口。具体用途：
  - §5.6 阶段 B 退还时按 `(p.owner, p.species)` 一一对应退还，不需要扩张顺序；
  - §6 计分时若采用"按扩张时间加权"，扩张顺序记录发挥作用；当前 §6 是 [TBD]，未来 §6 写作时确认是否使用。
  - §5.4 旧版"最后扩张的树"判定已在本轮 v0.2-draft-r12 **废除**——本条不再绑 §5.4。
  - §7 会给出具体的"扩张顺序"记录规则与写入字段。
- **[已确认]** 本章不规定扩张节奏、次数限制、强制扩张、跳格扩张等——这些是 §7 的范畴。

## 6. 计分与胜负  [本轮新增 v0.2-draft-r13]

> 本章基于用户原话："每一个玩家所有健康的植物中，每有一格土地块的草算1分、花2分、树4分（如果同一地形块内有多个土地块，多次计算），游戏结束时，分数最高获胜"。

### 6.1 计分公式（[已确认]）

每位玩家 P 的最终得分 `S(P)` 按下列公式计算：

```text
S(P) = Σ_{p ∈ plants(P), p.form == HEALTHY}  weight(p.species)
```

其中物种权重表：

| 物种 | 单棵得分 `weight` | 备注 |
| --- | ---: | --- |
| **草（GRASS）**  | **1** | 基数种，最低门槛 |
| **花（FLOWER）** | **2** | 标准种 |
| **树（TREE）**   | **4** | 主力种，最高门槛 |

> 计分对每位玩家**独立计算**——按 `p.owner` 归属到对应玩家的总分。

### 6.2 计分维度（[已确认]）

- **[已确认]** **计分单位 = 单棵 HEALTHY 形态的植物**——一棵算一棵，按物种权重计分。
- **[已确认 · 用户原话]** **同一地形块内有多个土地块，多次计算**：
  - 一格同时有"P1 草 + P2 花 + P3 树" → 该格贡献给 P1 = 1、P2 = 2、P3 = 4。
  - 一格同时有"P1 草 + P1 花"（同主多物种） → 该格贡献给 P1 = 1 + 2 = 3。
  - 一格只有"P1 草" → 该格贡献给 P1 = 1。
  - 同物种在同一格只能有一个主人（§5.1 已锁定）——所以一格不可能有"2 棵草"，不会出现一格的分数被该物种重复加倍的极端情形。
- **[已确认]** **WATER_SHORT 与 WITHERED 形态不参与计分**——按 §5.3 与 §5.7 锁定的形态语义。
- **[已确认]** **不计地块数、land_region 数**：计分 = 健康植物数 × 物种权重；与植物所在的 land_region 数量无关、不与 tile 数挂钩。
- **[已确认]** **计分只在终局触发一次**——不存在"中途计分"或"得分阶段性累加"。
- **[已确认]** 计分与植物的"扩张时间 / 扩张顺序"无关——只看终局时的物种与形态。这与 §5.8 中"扩张顺序字段为未来接口保留"的语义一致（当前 §6 不消费扩张顺序）。

### 6.3 胜负判定（[已确认]）

游戏结束时（§7.3）按下列顺序裁决：

1. **[已确认]** **先做形态终局结算**（§5.7）——缺水植物升级枯萎，保证终局时点形态锁定。
2. **[已确认]** **再按 §6.1 计算每位玩家得分**。
3. **[已确认]** **分数最高的玩家获胜**——按用户原话"游戏结束时，分数最高获胜"。
4. **[已确认]** **平局处理（[待确认]** — §9 #26）：当前默认"双方并列胜出"，未引入破平机制；后续可追加加赛、按扩张时间先后、随机裁决等。

> 关键点：
>
> - 胜负**不依赖**形态转变历程——只看终局形态。即使某棵植物"曾经健康过、终局时已缺水 / 枯萎"，也不计分。
> - 胜负**不依赖**地块归属——只看"哪个玩家拥有这棵植物"。地块归属与玩家拥有是两件事（详见 §5.1 / §9 #25）。

### 6.5 封闭与未封闭 land_region 的算分修正（[已确认 · 本轮新增 v0.2-draft-r14]）

> 基于用户原话："游戏结束时，如果某个土地块没有封闭，则其中所有健康的花和树得分减半"。

#### 6.5.1 修正公式（[已确认]）

§6.1 的基础计分公式在终局按本节规则修正——引入 land_region 的封闭状态作为修饰因子：

```text
S(P) = Σ_{L ∈ land_regions}  Σ_{p ∈ plants(P) ∩ L, p.form == HEALTHY}  weight(p.species) × multiplier(L, p.species)

multiplier(L, species) = {
    1.0    if L is land_closed (土地块封闭)
    1.0    if species == GRASS  (草不参与减半)
    0.5    otherwise           (未封闭 land_region × 非草 → 减半)
}
```

> **关键点**：
>
> - **"土地块没有封闭"** 在本规则书里特指 `land_region` L 的 land 边**未**全部被对接——即 L 仍然存在至少一条可拼接的 land 边（L 不是 `land_closed`），水网的封闭状态**不影响**本判定。
> - **只有花（FLOWER）和树（TREE）参与减半**——草（GRASS）不减半。这是用户原话"所有健康的花和树得分减半"的精确落地。
> - 减半**针对单棵植物**——每棵满足"未封闭 land_region × 健康 × 花/树"的植物独立减半；同理，一格多物种时花/树减半、草不减半。
> - 减半的判定**只发生在终局计分时**——结算过程 V_L / 形态分配 / 退还等都**不**受减半影响。
> - **WATER_SHORT 与 WITHERED 形态仍然不参与计分**（与 §6.2 一致）；减半仅对 HEALTHY 形态下的花 / 树生效。

#### 6.5.2 与既有规则的耦合（[已确认]）

- **[已确认]** **与 §5.6 全封闭结算独立**：本节判定的是计分时的 land 边封闭状态；§5.6 全封闭结算在主循环和终局做"退还种子 + 清场"——这两条**互不替代**。例如一个 land_region 既不是 `land_closed`、但其中的 WATER_SHORT 植物在 §5.6 阶段 A 升级枯萎时，会以 WITHERED 形态被移除——不留到计分；本节只关心仍然存活到终局 §6 计分时的 HEALTHY 植物。
- **[已确认]** **与 §5.7 终局升级的关系**：§5.7 在终局把 WATER_SHORT 升级为 WITHERED。WITHERED 不参与 §6 计分（§6.2）。所以"未封闭减半"对那些植物没有影响（已经退场）。**减半只对终局时仍处于 HEALTHY 形态的花 / 树生效**。
- **[已确认]** **与 §6.3 平局处理的关系**：平局判定基于"修正后得分"（即经过本节减半处理后的最终 `S(P)`）；不是基础分。

#### 6.5.3 公式示例（[已确认]）

> **示例**：玩家 P 拥有 3 棵 HEALTHY 的花，分布在 3 个 land_region 上：A 封闭（×1.0）、B 未封闭（×0.5）、C 未封闭（×0.5）。
>
> - P 在 A 上的花：1 棵 × 2 × 1.0 = 2 分；
> - P 在 B 上的花：1 棵 × 2 × 0.5 = 1 分；
> - P 在 C 上的花：1 棵 × 2 × 0.5 = 1 分；
> - 该 3 棵花的总贡献 = 2 + 1 + 1 = 4 分（若全封闭 = 6 分，未封闭的情况下掉了 2 分）。
>
> **示例**：玩家 P 在一个未封闭的 land_region L 上有 1 棵草 + 1 棵花 + 1 棵树（均为 HEALTHY）。
>
> - 草：1 × 1 × 1.0 = 1（草不减半）；
> - 花：1 × 2 × 0.5 = 1；
> - 树：1 × 4 × 0.5 = 2；
> - 该 land_region 总贡献 = 1 + 1 + 2 = 4（若全封闭 = 1 + 2 + 4 = 7，掉了 3 分）。

#### 6.5.4 章节接口（[已确认]）

- **封闭判定** = `land_region` 的 land 边封闭状态 → 已在 §5.6.1 定义 `land_closed`，本节复用；
- **水网封闭** = 与本节**无关**——仅 land 边封闭就足以触发"不减半"；
- **终局计分时点** = §7.3.2 终局结算流程的第 2 步——本节落在 §6.1 公式的修饰层，调用接口不变；
- **未限定变种**：减半规则对**所有 game_end 计分场景**生效（独玩 / 多人 / 河图 vs 山图变种统一适用）——若未来扩展"无变种"再单独定义。

### 6.4 章节接口（[已确认]）

- 计分对象 = 玩家拥有的 HEALTHY 形态植物 → 依赖 §5.1 / §5.3。
- 计分时段 = 游戏结束 → 依赖 §7.3 终局触发。
- 平局处理 → 见 §9 #26。
- 未封闭 land_region 的减半 → 详见 §6.5。

## 7. 回合流程  [本轮新增 v0.2-draft-r13]

> 本章基于用户原话："游戏开始时，每名玩家从河流牌堆中抽取一张，合法放置在地图上，直到河流牌被抽完；接下来每名玩家需要在自己的回合做一下事情：1、从地形牌堆抽一张牌，合法放置在地图上；2、选择一项：扩张 / 种植 / 跳过；3、回合结束，进入下一个玩家的回合；直到所有地形块被抽完放置完，游戏结束，最后结算分数"。

### 7.1 初始化与开局长牌阶段（[已确认]）

#### 7.1.1 初始化（[已确认]）

1. **[已确认]** 棋盘以起始地块开局（具体规格见 §2.6 [TBD]，策划案起手式已实现 4-land 起始地块）。
2. **[已确认 · 本轮新增 v0.2-draft-r14]** **发放种子**：每位玩家获得 3 种植物种子各 **2 枚**——草 / 花 / 树各 2，共 6 枚。这是用户原话"每名玩家开局时有 3 种种子个两个"的精确落地。§9 #27 锁定为本数字。
3. **[已确认]** **确定玩家回合顺序**：随机或商定，**当前默认按座位顺时针**（§9 #28 后续确认独玩 / 多人模式）。

#### 7.1.2 长牌阶段（[已确认]）

**长牌阶段（River Setup Phase）**在初始化之后、主循环之前进行：

- **[已确认]** **按 §7.1.1 第 3 步确定的玩家顺序，依次**为每位玩家完成下列动作：
  1. 从**河流牌堆**抽取 1 张河流地块；
  2. **合法放置**该地块（拼接规则按 §3.2 全部约束，包括 BANK ↔ 水口的水渠改写）；
  3. 完成本轮的长牌动作，进入下一位玩家。
- **[已确认]** **长牌阶段终止条件**：当河流牌堆被抽完时，长牌阶段结束——按用户原话"直到河流牌被抽完"。
- **[已确认]** **河流牌堆容量**：**当前默认 = 玩家数 N**（每玩家抽 N 张；总张数 = N）。是否每局随机抽取 / 包含全部河流地块 / 其他牌堆规格见 §9 #29。
- **[已确认]** **长牌阶段不进行扩张 / 种植 / 跳过动作**——只放牌，不触发植物相关行为、不触发 §5.4 / §5.6 结算。

> 关键点：
>
> - 长牌阶段的目的是"建立初始河流骨架"——为后续玩家在地形扩张时提供 BANK 与潜在的水口。
> - 长牌阶段放置的合法地块**会**触发 §3.6 的 `BANK ↔ 水口 → 水渠` 永久改写——与主循环放牌共用同一拼接逻辑。

### 7.2 玩家回合（主循环）[已确认]

每位玩家在自己的回合中，**依次**执行下列三步：

#### 7.2.1 第一步：从地形牌堆抽 1 张牌（必做）[已确认]

- **[已确认]** 从**地形牌堆**抽取 1 张地形地块（不可跳过、不可重抽）。
- **[已确认]** **该地块至少有一种朝向可合法放置时，玩家必须放置**——按用户原话"合法放置在地图上"。
- **[已确认]** **若抽到的地块完全没有合法朝向**（即任何朝向都不满足 §3.2 拼接约束），则该地块直接进入**弃牌堆**，本步结束，本玩家**不抽第二张**。
- **[已确认]** **合法性判定复用 §3.2 全套规则**——包括 BANK 改写、IR 跨界接口、中心地形约束（§2.4）。
- **[已确认]** **抽到的地块**经本次合法放置即落定；其"新放置"属性在本回合 §7.2.2.B 中作为种植动作的候选格（详见 §7.2.2.B）。

> 关键点：
>
> - "不可重抽"与卡卡颂原版一致——遇到不能放的地块，自认倒霉。
> - 放下的地块**必然**触发 §3.6 的拼接事件伪代码（含水渠改写、IR 接口计算、V_L 重算的入口标记）。

#### 7.2.2 第二步：选择一项动作（必做）[已确认]

从下列三项中**任选一项**执行——不能多选、不强制。

#### A. 扩张（Expand）[已确认]

- **[已确认]** 玩家从自己**所有可扩张的植物**中**任选一棵**——按用户原话"可以选择任意可扩张的植物"。"任意"指选任一棵，不是任选多种。
- **[已确认]** **可扩张**的定义：该植物所在 `land_region` L 周围至少存在一个合法的扩张目标格 `t`（满足下列全部检查）。
- **[已确认]** **扩张目标格合法性前置检查**（在扣种子之前执行，**失败则本扩张动作整体作废**，不扣种子、不留痕迹）：
  1. 目标格 `t` 必须**与已有己方植物所在 `land_region` L 相邻**（与 §5.8 检查 #1 一致）；
  2. **[已确认 · 本轮新增 · 用户原话]** 目标格 `t` 上**不能**已有**任何玩家**的**同物种**植物——即不论是自方同种还是异方同种，撞同物种视为非法。这是 §5.8 检查 #2 的加强版：§5.8 仅锁定撞同种异主非法；§7.2.2.A 额外禁止撞同种同主（"撞自己已有的该物种植物同样不可扩张"）。这是用户原话"没有相同的植物的土地块"的直接落地。
  3. 目标格 `t` 上**可以**已有"不同物种的植物"——例如在已有 P2 花的格子上扩张 P1 的草合法（不同物种），也允许在没有任何植物的格子上扩张任一物种；
  4. 其余前置检查复用 §5.8 已锁定的 §5.8 检查 #3。
- **[已确认]** 玩家扩张消耗**对应种类**的种子 1 枚（草 → 草种子、花 → 花种子、树 → 树种子）；种子从玩家自己的种子集合中扣除（不允许跨玩家借种）。
- **[已确认]** 扩张放置的新植物初始形态由 §5.4 / §5.5 判定——按 §5.8 已锁定的"扩张时点形态"。
- **[已确认]** 每回合**最多**执行 1 次扩张动作（一次扩一棵）——一回合只能选一项动作。

> 关键点：
>
> - 本回合§7.2.2.A 触发的扩张只走一棵——不强制扩尽所有可扩张植物；
> - 扩张动作**可作用于自己任何 land_region 上已有的植物**——包括本回合刚种植的植物（详见 §7.2.2.B 与 §7.2.3 的时序关系）；
> - 扩张顺序按动作时点写入（详见 §5.8 中"扩张顺序由玩家行为序列决定"——§7.2.3 维护一张全局扩张顺序表）。

#### B. 种植（Plant）[已确认]

- **[已确认]** **仅限**当玩家**本回合新放置的地形块 t_new**（即 §7.2.1 抽到并合法放置的 tile）满足下列全部条件时，才能发起"种植"：
  1. **t_new 包含土地**——即 t_new 至少有一条 `LAND` 边 或 中心为 `CENTER_LAND`（详见 §2）；
  2. **t_new 所属的 `land_region` L_new 内没有别人的植物**——即除本玩家 P 之外，L_new 上没有任何植物（即"该 land_region 当前归我独有或新开"）。
- **[已确认]** 玩家**任选一种物种**（草 / 花 / 树）作为本次种植的目标，从种子集合中扣除 1 枚对应种类种子，**在 t_new 上的土地上种一棵**该物种的植物。
- **[已确认]** **同主多物种合法**——只要 t_new 上没有该玩家已有同物种植物（被 §7.2.2.A 检查 #2 自动排除），玩家可在同一 land_region 多格上选种不同物种，**形成"P1 草 + P1 花 + P1 树"同主多物种的多格分布**。
- **[已确认]** **种植 vs 扩张的关键区别**：
  - **种植**只能在本回合新放置的 tile（t_new）上发生；
  - **扩张**可以从自己任一已有 land_region 的相邻格（任何格子，不限于 t_new）发起。
- **[已确认]** **种植动作的"无主 land_region 才可种"边界**——若 L_new 上已有其他玩家任意植物，则 §7.2.2.B 第 2 条不满足，种植动作不可发起；玩家转而选 A 或 C。

> 关键点：
>
> - 种植的形态初始判定按 §5.4 / §5.5 走——若 L_new 的 V_L ≥ 种植物种的 `p.need`，该棵新植物 HEALTHY；否则 WATER_SHORT。
> - 种植**不等于"对自己已有 land_region 的相邻扩张"**——后者走扩张动作分支。
> - 种植**仅**对本回合新放置的 t_new 开放——不允许"种植到 N 回合前已放置的 tile"（那是扩张动作的范围）。

#### C. 跳过（Pass）[已确认]

- **[已确认]** 玩家**跳过本步骤的全部动作**——不扩张、不种植，直接进入 §7.2.3。
- **[已确认]** 跳过的回合**不影响**植物的形态判定——§5.4 / §5.5 / §5.6 / §5.7 各自的结算时点照常工作。

#### 7.2.3 第三步：回合结算窗口与顺序轮转（[已确认]）

玩家执行完 §7.2.2 选定动作（或跳过）后，进入**结算窗口（Settlement Window）**：

1. **[已确认]** **重算所有 `land_region` 的 V_L**（按 §4）；
2. **[已确认]** **重分配水源**（按 §5.5）；
3. **[已确认]** **判定所有植物的形态**（按 §5.4）；
4. **[已确认]** **检查所有 `land_region` 的全封闭状态**（按 §5.6.1）；
5. **[已确认]** **执行 §5.6.2 的两阶段结算**（阶段 A 升级枯萎；阶段 B 退还种子 + 清场）；
6. **[已确认]** **记录本回合扩张顺序**（§5.8 中"扩张顺序字段"在结算窗口末尾写入）。

随后：

- **[已确认]** 结算完成后进入下一位玩家（按 §7.1.1 第 3 步确定的玩家顺序）。
- **[已确认]** **结算** = 玩家动作**之后立即触发**，下一位玩家行动**之前**完成；这样每位玩家行动前的棋盘形态是稳定的。

> 关键点：
>
> - 结算窗口是 §5 全部形态与退还规则的触发器——每次回合切换都重新走一遍；
> - 结算后的玩家回合状态必须是**稳定**的——下一位玩家看到的棋盘 = 该回合结算后的棋盘；
> - 一位玩家的扩张动作若触发了 §5.6 全封闭结算（阶段 B 退还），则在结算窗口内立即执行——下一位玩家看到的是已退还后的稳定状态。

### 7.3 终局触发与最终结算（[已确认]）

#### 7.3.1 终局触发条件（[已确认]）

- **[已确认]** **当且仅当**地形牌堆被抽完且**所有抽出的合法地形地块已被放置**时，游戏结束——按用户原话"直到所有地形块被抽完放置完，游戏结束"。
- **[已确认]** **触发位置**：当前回合（§7.2.3）结算窗口**结束后**——本回合**不进入下一位玩家**，直接走 §7.3.2 终局流程。
- **[已确认]** **§7.2.1 抽到的地块若最终被弃置**（无法合法放置），它**不计入**"已放置"集合——游戏继续；只有当抽到的合法地块全部被放置、且牌堆为空时，游戏才结束。

> 关键点：
>
> - "抽完且放置完"是**复合终止条件**——既要求牌堆空，又要求所有合法抽取的地块都已被处理（放置或弃置不影响终止）。
> - 现行玩家的最后回合仍然完整执行 §7.2.1 / §7.2.2 / §7.2.3——直到 §7.2.3 结算窗口结束才检查终局条件。

#### 7.3.2 终局结算流程（[已确认]）

1. **[已确认]** **§5.7 游戏结束结算**（终局形态升级）：
   - 重算所有 V_L（§4）；
   - 重分配水源（§5.5）；
   - 判定所有植物形态（§5.4）；
   - 所有 WATER_SHORT 形态植物 → WITHERED（§5.7 阶段 2）；
2. **[已确认]** **§6 计分**：按 §6.1 / §6.2 计算每位玩家得分；
3. **[已确认]** **宣布胜负**（§6.3）：比较得分，最高分者胜出。

#### 7.3.3 终局后的退还 / 清场（[已确认 · 本轮新增]）

- **[已确认]** **终局不再触发 §5.6 阶段 B 的退还与清场**——按 §5.7 已锁定的"游戏结束结算仅升级枯萎，不退还种子"。退还路径已在主循环的 §7.2.3 结算窗口里持续处理；终局不再额外退还。
- **[已确认]** WITHERED 形态的植物若在主循环结算中未被 §5.6 退还，仍保留至终局——它们**不参与 §6 计分**（按 §5.3 / §6.2）；终局后游戏即结束，无需处理。
- **[已确认 · §9 #23]** 若后续设计希望 §5.6 与 §5.7 在退还行为上对齐——可在下一轮把"游戏结束也触发退还"加进 §7.3.2。当前默认**不同步**。

### 7.4 边界与关键点（[已确认]）

- **[已确认]** **种子用完即停**：当玩家某物种的种子为 0 时，该物种的扩张 / 种植动作不可发起——玩家只能选"种植其他物种的种子"或"跳过"，或干脆"跳过本步"。
- **[已确认]** **动作选择与回合顺序解耦**：玩家本回合扩张消耗的种子不会影响其他玩家的动作——植物形态的变更集中在 §7.2.3 结算窗口同步生效。
- **[已确认]** **持续结算的设计含义**：每位玩家每次行动后都会触发一次结算窗口；这与"只在游戏结束结算一次"的传统桌游不同——本规则书把 §5.6 全封闭退还从"终局一次性"搬到"每回合持续性"——保证玩家能在每一步看到"自己退种 / 自己清场"的反馈。
- **[已确认]** **玩家顺序与游戏结束**：最后一位玩家执行完自己回合后，若牌堆已空，则不再轮转，直接进入 §7.3 终局流程；具体哪个玩家的最后回合触发了终止，由游戏运行时的牌堆剩余数决定（不再引入"最后 N 圈"之类限制）。
- **[已确认]** **独玩模式（待确认** — §9 #28）：若仅 1 位玩家，跳过玩家顺序轮转，玩家始终同一回合；其它规则（开局、单步流程、终局）保持不变。
