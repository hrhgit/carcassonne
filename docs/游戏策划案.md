## 1. 游戏概述

### 1.1 一句话说明

玩家轮流拼接由**土地、水流、空地**构成的方形地块，在有限的水网中种下植物、让植物向相邻土地蔓延；只有持续获得足够水分的土地能维持生长和得分。

### 1.2 核心体验

- **[已确认]** 拼接时先看边缘是否能接上，再考虑这一步会不会改变土地和水网的连通关系。
- **[已确认]** 植物的扩张会把相邻土地变为玩家的领地；土地越大，供水压力越高。
- **[已确认]** 水不够时，土地上的植物会死亡／枯萎，不能把无限扩张当成唯一正确策略。
- **[提案]** 游戏的乐趣来自“扩张、供水、封锁和风险控制”之间的取舍，而不是单纯把同色区域拼大。

### 1.3 首个可玩版本的目标

先做一个能完整结算的桌面策略切片，而不是先堆很多地块美术或植物品种：

1. 放置并旋转地块；
2. 验证四条边的匹配；
3. 计算连续土地与连续水网；
4. 种植、扩张、供水和枯萎；
5. 显示归属与分数。

首个切片可先以单人沙盒验证规则；通过后再加入轮流对抗的多人回合。

## 2. 名词表

| 名词 | 定义 |
| --- | --- |
| **地块（Tile）** | 一张可旋转、可放入方格棋盘的方形拼图。 |
| **边口（Edge Port）** | 地块北、东、南、西四条边之一的连接语义。 |
| **土地边** | 由可种植土地完整覆盖的一条边。 |
| **水口** | 位于一条边正中心的窄水流端点。 |
| **空地边** | 没有土地或水口的草地／留白边。 |
| **土地块（Land Region）** | 一张地块内部彼此连通的一块可种植区域；同一张牌可以有多个彼此分离的土地块。 |
| **土地群（Land Component）** | 通过相邻土地边连接而成的跨地块连续土地块。它是植物归属、面积和需水量的主要结算对象。 |
| **水网（Water Component）** | 通过相邻水口连接而成的连续水路网络。 |
| **灌溉接点（Irrigation Link）** | 地块内部水流真正抵达一个土地块的位置，表示该土地块可从该水网取水。 |
| **土地单位（Land Unit）** | 用于供水和计分的最小面积单位。v0.1 中，一个独立土地块默认为 1 单位；较大的区域可在地块定义中提高其权重。 |

## 3. 核心回合流程

### 3.1 标准回合

**[提案]** 每名玩家依次执行以下流程：

1. **获得地块**：从公共牌堆翻出一张地块；是否允许手牌与选牌见“待确认事项”。
2. **旋转与预览**：玩家可将地块以 90° 为单位旋转。
3. **合法放置**：放入与已有地块正交相邻的空格；所有接触边必须匹配。
4. **重算地图**：更新土地群、水网和灌溉接点。
5. **种植／扩张**：玩家可在可用土地上种下新植物，或让自己已健康生长的植物向相邻未占土地扩张。
6. **供水结算**：计算每个土地群的需求和可获得水量。
7. **状态与计分结算**：健康植物成长、缺水植物枯萎，更新归属与分数。
8. **回合结束**：交给下一位玩家；牌堆用尽后进入最终结算。

### 3.2 为什么供水放在扩张之后

**[提案]** 新增的土地应立刻计入需求。因此玩家可以在本回合做一次大胆扩张，但若水网没有跟上，会在同一次结算中暴露风险。这使“先修水还是先抢地”成为清晰决策。

## 4. 地块拼接规则

### 4.1 方形棋盘与旋转

- **[已确认]** 地块由四条边构成：北、东、南、西。
- **[提案]** 棋盘采用正交方格；地块只能以 0°、90°、180°、270° 旋转。
- **[提案]** 新地块必须至少与一张已有地块边对边相邻；不能只角碰角。

### 4.2 边口类型

**[已确认]** v0.1 的每条边有且只有一种类型：

```text
EMPTY  空地边
LAND   土地边
WATER  水口
```

**[已确认]** 同类型边才能相连：

| 接触边 | 是否合法 | 结果 |
| --- | --- | --- |
| 土地 ↔ 土地 | 是 | 两侧土地加入同一个连续土地群。 |
| 水口 ↔ 水口 | 是 | 两侧水流在边中心点相接，加入同一个水网。 |
| 空地 ↔ 空地 | 是 | 地貌平滑相接，但不形成土地或水的资源网络。 |
| 任何不同类型 | 否 | 该位置不能放置。 |

边界外侧不需要匹配；只有与已放置地块实际接触的边参与校验。

### 4.3 视觉与拓扑约束

- **[已确认]** 水口必须落在边的**精确中心点**，并以细窄水流进入地块内部。
- **[已确认]** 土地一旦占据一条边，视觉上必须覆盖**整条边**，不能用一小块土斑假装土地边。
- **[已确认]** 水流必须在地块内部抵达至少一块土地；禁止只通往空地、没有灌溉意义的孤立水段。
- **[已确认]** 多水口地块可以在中心形成主水道，再以短支流灌入相邻土地。
- **[提案]** 当前“一条边一种类型”的规则保持到首个可玩版本。若未来要做“水流穿过土地边”等复合边口，应新增明确的 `COMPOSITE` 拓扑类型，不能悄悄放宽现有匹配规则。

### 4.4 土地边数量：四个主类型

**[已确认]** 土地按占据 1、2、3、4 条边分成不同主类型；旋转只是同一类型的朝向变化，不是新类型。

| 主类型 | 土地边数 | 设计作用 | 当前原型示例 |
| --- | ---: | --- | --- |
| 单边土地 | 1 | 小型起点、狭窄扩张、容易受水限制。 | `one_edge` |
| 双边土地 | 2 | 可做两块独立土地或一块连通土地，形成分叉选择。 | `two_edges` |
| 三边土地 | 3 | 大面积扩张机会，也带来更高需水压力。 | `three_edges` |
| 四边土地 | 4 | 四向核心土地，适合成为大型土地群中心。 | `four_edges` |

**[提案]** “土地边数”只定义主分类，不能替代内部拓扑。比如双边土地至少应支持两种变体：

- 两条边各自连接到两块独立土地；
- 两条边在地块内部属于同一片土地。

这项区分决定植物能否从一条边扩张到另一条边，也决定需水面积，必须在正式地块数据中显式保存。

### 4.5 合法性伪代码

```text
for 每一条与已放置邻居接触的边:
    if 新地块.边类型 != 邻居.相对边类型:
        拒绝放置

接受放置后:
    合并相接的土地群
    合并相接的水网
    重新建立水网到土地块的灌溉接点
```

## 5. 土地、植物与归属

### 5.1 土地的可视状态

**[已确认]** 每块可种植土地需要至少有以下视觉状态：

| 状态 | 含义 | 视觉要求 |
| --- | --- | --- |
| `BARE`（裸土） | 尚未种植或没有活植物。 | 棕色土壤，能和空地清楚区分。 |
| `GROWING`（成长） | 有足够水分、正在生长。 | 植物覆盖土地，但仍可看出土地轮廓。 |
| `WILTED`（枯萎） | 因供水不足死亡。 | 枯黄／暗沉，不能与健康植物混淆。 |

目前原型中的点击种植只验证视觉状态切换；它还不是完整的占地、扩张或供水系统。

### 5.2 种植

- **[已确认]** 玩家可以把植物种在土地上。
- **[提案]** 每回合玩家拥有一次“植物行动”：在一块未归属、可灌溉的裸土地块上播种，或将一块自己健康的土地群扩张一次。
- **[提案]** 首次种下植物后，该土地块立即标记为该玩家归属，但要等供水结算通过才成为健康生长状态。
- **[待确认]** 是否允许在尚未接到水的土地上“冒险播种”，等待未来修通水网；v0.1 建议禁止，以免状态含义模糊。

### 5.3 扩张与连通

- **[已确认]** 植物会在相邻土地上成长，成长后的土地归玩家并可得分。
- **[提案]** “相邻”只指通过边相接且属于同一土地群的正交连接；对角线不算相邻。
- **[提案]** 每个健康土地群在其拥有者的结算阶段最多扩张 1 个土地单位。由玩家从合法相邻的未归属土地中选择目标；只有一个目标时可自动扩张。
- **[提案]** 一块新扩张的土地在同一轮立即增加需水量，但不再连锁扩张，避免单回合滚雪球。
- **[提案]** v0.1 不允许健康植物直接夺取另一位玩家的健康土地。边界竞争通过抢先连接、截断水网或占据关键地块实现；明确的“侵占”机制留到后续版本。

### 5.4 归属与枯萎

**[提案]** 土地群记录 `owner_id`、`growth_state` 和 `land_units`。植物枯萎时：

- 土地仍显示原玩家的淡化归属标记；
- 枯萎土地不产生分数，也不能继续扩张；
- 重新获得足够水分时，是否自动复苏、是否需要再次播种，暂定为 **[待确认]**；v0.1 建议需要一次新的植物行动，避免“断水没有代价”。

## 6. 水网与供水规则

### 6.1 水路不是水源

**[提案]** 水口和水路只说明“水能走到哪里”，并不自动产生水。每个水网需要至少一个带容量的**水源**，例如泉眼、上游河口或蓄水池地块；没有水源的连通水路供水量为 0。

这项区分是必要的：否则只要把水口接成闭环，就会无成本地养活无限大的土地。

### 6.2 供水模型（v0.1 默认提案）

对每一个水网，结算：

```text
水网供给 S = 该水网内所有水源容量之和
土地群需求 D = 该土地群的土地单位数 × 每单位需水量
水网总需求 T = 被该水网灌溉的所有健康／新种植土地群的 D 之和
供水比 R = min(1, S / T)
```

初始平衡常数建议：

| 参数 | v0.1 建议值 | 意义 |
| --- | ---: | --- |
| 每土地单位需水量 | 1 | 地图规模和水源容量统一用“水滴”表示。 |
| 小型泉眼容量 | 3 | 能稳定供养约 3 个土地单位。 |
| 河流／大水源容量 | 6 | 形成值得争夺的水网核心。 |
| 缺水判定阈值 | `R < 1` | 水网无法满足其已灌溉土地的完整需求。 |

### 6.3 供水分配与缺水

**[提案]** 为避免同一滴水被重复计算，v0.1 使用下列确定性规则：

1. 一个土地群若接触多个水网，选择到最近水源的水网为其“主灌溉水网”；距离相同时用稳定的内部 ID 打破平局。
2. 一个水网只对分配给自己的土地群结算总需求。
3. 当 `R = 1` 时，所有相关植物健康成长。
4. 当 `R < 1` 时，所有相关土地群进入缺水；在该次结算中有植物的土地变为 `WILTED`。

这一规则刻意简单、可预测，适合第一个切片。后续若要表现复杂的分渠、优先级或蓄水，可以把它换成真实的水量分配图算法，但不能改变“土地规模会提高总需求”这一核心张力。

### 6.4 灌溉接点

- **[已确认]** 每条视觉水流都必须接触至少一个土地块。
- **[提案]** 只有存在内部灌溉接点的土地块，才能从相连水网取水；“水路从旁边经过”不应自动供水。
- **[提案]** 地块数据应把水路与土地块的接触关系保存为显式数据，而不是在渲染像素上判断。

### 6.5 未来可选的深化方向

这些不是 v0.1 的必做项：

- 不同植物有不同需水量、耐旱性和得分方式；
- 水库可存水，旱季降低水源容量；
- 水渠存在方向、坡度、闸门或传输上限；
- 玩家可以修建一次性灌溉设施，改变一个灌溉接点。

## 7. 计分与胜负

### 7.1 已确认的计分原则

- **[已确认]** 植物成长并占有土地后，玩家可以由该土地得分。
- **[已确认]** 不能持续供水的植物会死亡，因此不应按“曾经占过多少地”无条件累计收益。

### 7.2 v0.1 计分提案

**[提案]** 在每次回合结算末：

```text
本回合得分 = 玩家所有健康土地群的土地单位总数
```

| 土地状态 | 是否计分 | 原因 |
| --- | --- | --- |
| 健康成长 | 是 | 奖励能被水网长期维持的扩张。 |
| 刚扩张且本回合水量足够 | 是 | 扩张立即有收益，也立即带来风险。 |
| 裸土 | 否 | 没有植物就不应产生领地收益。 |
| 枯萎 | 否 | 缺水是实际代价，不只是视觉效果。 |

这个公式会让“大地块 + 大水网”稳定得分，而盲目扩张会拉低整个水网的供水比。首个可玩版本不加入完成地形奖励，先把供水张力验证清楚。

### 7.3 游戏结束

**[提案]** 公共牌堆用尽后，每位玩家再完成一次同等数量的回合，进行最终供水结算；总分最高者获胜。

**[待确认]** 需要确定：牌堆大小、玩家人数、是否有季节／固定回合数，以及平局的决胜方式。

## 8. 地块数据设计

### 8.1 静态定义与运行时状态必须分开

**[提案]** 一张牌的可编辑定义不能直接承载游戏中的归属、植物状态或当前水量。建议区分：

```text
TileDefinition（静态、可复用 Resource）
  ├─ id / 名称 / 固定美术预制件 / 预制件基础朝向
  ├─ 北东南西四条边的 EdgeKind
  ├─ land_regions：每一块土地的边接入与土地单位数
  ├─ water_paths：水口之间和水口到灌溉接点的内部连通关系
  ├─ irrigation_links：水路可以灌溉哪些 land_region
  └─ source_capacity：没有水源时为 0

PlacedTile（运行时实例）
  ├─ 棋盘坐标与旋转角度
  ├─ 玩家归属与各土地块的生长状态
  ├─ 当前所属的土地群／水网 ID
  └─ 用于界面的临时显示数据
```

### 8.2 当前原型对应关系

| 当前文件 | 已有职责 | 还缺什么 |
| --- | --- | --- |
| `scripts/tile_definition.gd` | 四条边的 `EMPTY / LAND / WATER` 定义、固定预制件与基础朝向。 | 土地内部拓扑、水路拓扑、灌溉接点和水源容量。 |
| `scenes/tiles/*.tscn` | 每种地块的固定土地、水流、空地美术；可在 Godot 中独立编辑。 | 后续可增加更丰富但仍与边口一致的局部细节。 |
| `scripts/tile_catalog.gd` | 牌堆、每个规则定义到固定预制件的映射。 | 扩充牌组与完整抽牌规则。 |
| `scripts/board_state.gd` | 正交邻接、四边匹配、占格与放置者记录。 | 土地群／水网连通性求解。 |
| `scripts/tile_view.gd` | 实例化固定预制件，并只做等比缩放、定位与 90° 旋转。 | 后续可增加不改变地块美术的状态标识。 |
| `scripts/main.gd` | 双人轮流放置、旋转、合法预览、HUD 与烟雾测试。 | 植物、供水、计分和最终结算。 |

### 8.3 运行时求解关系

```text
TileDefinition + BoardState
        │
        ├── 边口匹配校验 ──> 可否放置
        │
        ├── 土地并查集 ────> LandComponent（面积、归属、成长）
        │
        └── 水路并查集 ────> WaterComponent（来源、容量、灌溉对象）
                                      │
                                      └── 供水结算 ──> 成长／枯萎／分数
```

视觉节点负责显示这些结果，不负责自行推断归属或水量。这能让之后更换美术、增加动画或做存档时不破坏游戏规则。

## 9. MVP 范围与实施顺序

### 9.1 MVP-A：规则验证沙盒

目标：证明“地越大越难供水，缺水会阻止无脑扩张”是好玩的。

- 方格棋盘与地块旋转；
- 严格边口匹配；
- 单／双／三／四边土地的少量变体；
- 至少一种水源地块；
- 一名玩家的种植、每回合一次扩张、供水和枯萎；
- 分数与水量 HUD；
- 可重复运行的规则测试场景。

### 9.2 MVP-B：两名玩家的桌面回合

目标：验证拼接和水网是否产生真实对抗。

- 两名玩家轮流放置与种植；
- 公共牌堆与最终结算；
- 归属颜色和得分板；
- 不夺取健康植物的边界竞争；
- 至少一张共享水源、至少一张会造成供水竞争的地块。

### 9.3 暂不进入 MVP 的内容

- 多植物物种、科技树、天气、季节；
- 复杂水压、方向、真实流体模拟；
- AI 对手、在线匹配、完整剧情；
- 大量独立美术资产和高级特效。

这些都应等核心供水循环被验证后再排期。

## 10. 可验证的验收场景

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| V1 | 水口正中心对水口正中心放置。 | 合法；两个水段形成同一水网。 |
| V2 | 水口对土地边，或土地边对空地边。 | 不合法；放置预览明确提示冲突边。 |
| V3 | 放置一张有水口的牌，但水流未抵达任何土地。 | 地块定义校验失败，不能进入牌堆。 |
| V4 | 将单边土地接到已有土地群。 | 土地群面积增加 1，下一次供水需求相应增加。 |
| V5 | 水源容量为 3，已灌溉土地单位从 3 扩张到 4。 | 供水比低于 1；相关植物在结算时枯萎。 |
| V6 | 健康植物旁边出现同一土地群中的未归属土地。 | 玩家可选择一次扩张，新增土地记录归属。 |
| V7 | 枯萎土地存在于玩家领地。 | 它不计分、不能扩张，视觉上为枯萎状态。 |
| V8 | 两位玩家都试图利用同一个有限水源。 | 供水模型给出确定且可在 HUD 中解释的结果。 |

## 11. 待确认决策清单

以下项目会直接改变规则和数值，实施前需要确认：

1. **玩家人数与目标平台**：先做单人益智、2 人对抗，还是 2–4 人桌游体验？
2. **抽牌方式**：完全随机翻牌、公开市场，还是每人持有若干张牌？
3. **播种限制**：每回合一次植物行动是否合适；允许不通水的冒险播种吗？
4. **扩张选择**：保持“每土地群每回合扩张 1 单位”，还是改为自动扩散／使用资源加速？
5. **土地内部拓扑**：双边或三边土地是否允许分成多个独立土地块；各变体占牌堆的比例如何？
6. **水源归属**：水源由放置者拥有、全体共享，还是水网接入者都可使用？
7. **缺水恢复**：植物枯萎后需重新播种、自动复苏，还是永久死亡？
8. **冲突规则**：是否永远不能侵占对方土地；能否通过切断水网让对方放弃领地？
9. **分数节奏**：每回合按健康面积得分，还是仅在封闭／完成土地群时一次性得分？
10. **结束条件**：牌堆耗尽、固定轮数、季节轮替，或某个生态目标达成？

## 12. 下一步建议

按依赖顺序推进：

1. 给 `TileDefinition` 增加内部土地块、水路和灌溉接点数据；
2. 建立 `BoardState` 与旋转后的边口匹配校验；
3. 实现土地群／水网的连通性求解；
4. 用一个水源容量和“每土地单位需水 1”的数值完成供水结算；
5. 接入种植、一次扩张、枯萎和分数 HUD；
6. 运行第 10 节的验收场景，再调整数值和地块牌组。

在这六步验证前，不需要先制作大量地块。规则能否让玩家感到“我想扩张，但必须想办法让水跟上”，才是这个项目最重要的早期判断。
